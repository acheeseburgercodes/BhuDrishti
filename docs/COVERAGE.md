# How the coverage layer is calculated

Implementations: `backend/coverage.py` (authoritative) and `shared/src/coverage.js` (web and
mobile). Parameters: `shared/fixtures/coverage-model.json`. `shared/fixtures/coverage-parity.json`
is regenerated by `scripts/gen_coverage_parity.py`; both test suites must match it exactly.

The corridor bounding box is split into 0.02° cells (~2 km, 552 cells). For each cell centre:

```
contribution_i = range_i · freshness_i · reliability_i
coverage       = 1 − Π (1 − contribution_i)        # independent-sensor union
gap priority   = risk · (1 − coverage)
```

* **range** = `max(0, 1 − (d/R)²)`. `R` is an *assumed* sensing range (3 km ESP32, 1 km phone,
  overridable per node via `range_km`). It is not measured detection distance.
* **freshness** = 1 up to 5 min after `last_seen`, then linear to 0 at the freshness window
  (default 60 min, adjustable in the UI). Never-seen nodes contribute 0.
* **reliability** = reported `reliability` (0.8 when unknown) × 0.5 if battery <15 % (× 0.8 if
  <30 %) × 0.75 for `warning` status; 0 for `offline`.
* **risk** (proxy) = 0.15 + 0.6·exp(−d_river/2 km) + 0.25·settlement exposure, using a
  hand-digitised approximate river centreline (±1 km) and seed settlement populations.

Bands: covered ≥ 0.6, partial ≥ 0.25, otherwise uncovered. Uncovered cells are shaded by
risk so remote hillsides do not dominate.

## What it does **not** include

DEM / slope / valley shielding, radio propagation or backhaul, measured detection
probability, or authoritative hydrography. Treat it as a planning aid that shows where
sensing evidence is thin, never as a statement that an area is safe. Snapshots can be
stored in `coverage_samples` for trend review.
